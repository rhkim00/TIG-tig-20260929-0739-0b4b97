# 제품 설계와 의사결정 기준

P-013·023: PM, UX/UI, 개발, 운영 관점을 통합해 제안하고 실제 사용자 입력·시스템 응답 예시를 포함한다.
유찬이 최종 결정한다. 다음 기준은 제안과 리뷰를 일관되게 하기 위한 관점이며 미정 기능·정책을 자동 확정하지 않는다.

## 사용자 가치

사용자의 현재 코딩 작업이 끊겼을 때 얼마나 쉽게 이어갈 수 있는지, 여유 있는 사용자가 완료 가능한 작업으로 TIG를 얻는지를 기준으로 판단한다.
설치 수나 클릭 수만 보지 않고 실제 인계 성공, 수행 완료, TIG 획득 후 요청으로 이어지는 경험을 확인한다.
기존 AI 대화·로그인·프로젝트 맥락을 활용하고 같은 내용을 다시 입력하게 하는 부분을 줄인다.

## UX/UI

- 주요 행동과 현재 상태를 명확히 보여준다. 기술 내부 상태가 사용자의 선택에 필요할 때만 노출한다.
- 승인한 범위는 반복 확인하지 않는다. 예외가 생기면 해결할 항목만 묻는다.
- 실행 중·중단·실패·완료·정산을 구분한다. 실제 성공 전에 성공 문구를 표시하지 않는다.
- TIG 보상, 작업 범위, 필요한 실행 환경처럼 결정에 필요한 정보를 먼저 보여준다.
- 요약과 상세 보기를 나눠 이해에 필요한 정보를 제공한다. 예상시간·가용량을 확인 없이 채우지 않는다.
- 알림은 시점·빈도·거절/나중에 처리를 고려한다. 알림 수신이 자동 작업 수락으로 이어지지 않게 설계한다.

## 구현과 운영

정상 경로와 함께 재시도, 연결 끊김, 중복 실행/예치, 취소, 모델 미지원 상황을 설계한다.
추가 기능의 서버/로컬 작업량·계약·검증·지원 비용과 10일 일정 영향을 설명한다.
막연히 모든 기능을 우선 구현하지 않고 핵심 거래 완성에 대한 기여와 의존성을 비교해 유찬에게 제안한다.
기술적 가능성, 공식 지원, provider 허용, 실제 사용자 검증을 구분한다.

## 제안을 전달하는 방법

핵심 판단을 먼저 말하고 다음 중 그 결정에 필요한 내용만 짧게 포함한다.

- 사용자 문제와 권하는 안, 선택 이유
- 자연어/화면 UX 예시와 중요한 예외
- 구현/운영 부담 및 기존 결정과의 충돌
- 효과를 확인할 지표, 불확실한 가정
- 다음에 결정할 질문 하나

사소한 결정마다 모든 항목을 길게 나열하지 않는다. 추천 근거가 경험적 가설이면 검증된 효과처럼 표현하지 않는다.

## 현재 게시 UX 예시

> 사용자: 이 작업을 지정 모델, 1,000 TIG로 올려줘.
> 시스템: 게시했어요. 1,000 TIG를 예치했고 수행자를 찾고 있어요.

P-022에 따라 조건이 명확하면 추가 확인 없이 진행한다. 다만 실패하면 해당 이유와 필요한 다음 행동을 알려준다.
확인할 지표 후보: 게시 성공률, 게시까지 걸린 시간, 추가 질문 수, 중복/잘못된 게시와 취소율.
지표 수집/보존 범위는 기존 데이터 정책 결정 절차를 따른다.
