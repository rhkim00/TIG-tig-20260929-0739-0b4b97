# TIG 경제와 정산

## 현재 기준

기존 기준: 현금 구매·출금·직접 송금 없음. task escrow 및 ledger 사용.
근거와 확정 결정은 [확정사항](00_confirmed.md)을 따른다. 아래 질문은 별도 결정 전까지 모두 미결정이다.

## 포인트 명칭 — P-012

포인트 표기는 TIG다. 기존 WC-xxx는 질문 참조 ID로만 유지한다.
“TIG라는 티커”는 이번에 정한 포인트 단위이며 blockchain·현금 교환 도입을 뜻하지 않는다.
사용자 예시: “보상 1,000 TIG로 올려줘” → 게시 조건 충족 후 예치 → 작업 성공·승인 후 지급.
“Yes”는 작업 수락·수행·제출 승인이다(P-025). 직접 승인 시 지급(P-026) 또는 검토 기한 48시간 미응답 시 자동 지급(P-027)으로 정산한다.
1,000 TIG는 사용자가 제시한 예시 보상이며 전체 작업의 기본값이나 token 환율이 아니다.

## 게시·예치 승인 — P-022

작업·모델 조건·TIG 보상이 명확한 게시 명령으로 게시와 예치를 승인한다. 정상 경로에 별도 확인을 추가하지 않는다.
잔액·권한 부족 또는 조건 불명확 시 필요한 확인만 한다. 보상 금액을 임의 변경하지 않는다.
중복 게시/예치 방지와 부분 실패 복구를 함께 설계한다. 구체적인 DB transaction/API 계약은 아직 미정이다.

## 직접 승인과 미응답 자동 지급 — P-026·027

플랫폼 검사 → 요청자 최종 승인 → TIG 지급 순서다. 검사 통과나 수행자의 제출만으로 지급하지 않는다.
요청자의 명확한 승인 한 번으로 정산하며 성공 확인 후 지급 완료를 표시한다. 코드 병합은 별도다.
중복 승인·재시도는 같은 지급을 반복하지 않도록 설계한다. 원장·상태 전이·실패 복구 계약은 WC-07에서 정한다.
P-027: 검토 기한 48시간 동안 미응답이면 예치된 작업 보상을 자동 지급한다. 운영자 검토를 미응답 정산의 필수 단계로 두지 않는다.
직접 승인과 기한 만료가 겹쳐도 한 번만 지급하고 정산 사유를 구분해 기록한다. 서버에서 기한 정산을 처리하는 구체적 구현은 미정이다.
P-028: 검토 중 수정 요청/분쟁 접수 시 예치금을 요청자에게 전액 복구하고 거래를 종료한다. 수행자 지급은 없고 자동 지급 예약은 무효화한다.
복구는 새 TIG 발행이 아니라 해당 예치금을 사용 가능 잔액으로 돌리는 처리다. 지급과 환불은 동시에 성립할 수 없고 재시도에도 한 번만 정산한다.
기한 시작·알림·검사 실패, 이미 지급된 TIG의 회수/지급 후 신고 처리는 미정이다.

## 주간 지급과 미사용량 캠페인 — P-029·030

매주 TIG를 지급해 초기 사용자 확보와 반복 이용을 지원한다(P-029). 작업 수행만으로 획득한다는 기존 원칙에 주간 발행을 추가한다.
P-031로 구독 플랜·가격별 차등을 확정했다. 가격 기준은 P-032의 표준 플랜 가격이다. P-034로 구독 확인 직후 첫 지급과 이후 7일마다 자동 지급을 확정했다. P-041로 표준 USD 월 가격 1달러당 주 50 TIG, P-042로 두 종류 TIG 모두 만료 없는 누적을 확정했다. 세부 자격은 미정이다. 일회 가입 보상을 별도로 추가한 것은 아니다.
P-031에 따라 P-030 미사용량 캠페인과 추가 보너스는 보류하고 주간 기본 지급만 설계한다. 기존 작업 수행 보상은 유지한다.
P-032: 공식 도구에서 확인 가능한 플랜 등급을 Tokenisgold의 지급표에 연결하고 플랜의 표준 가격을 기준으로 금액을 정한다. 실제 개인 결제액 조회 또는 영수증 제출은 기본 UX에 요구하지 않는다.
P-041: 표준 미국 달러 월간 가격을 사용하며 연간 할인/실제 결제액은 반영하지 않는다. 주간 TIG = 표준 USD 월 가격 × 50이다. 실제 가격표 검증·소수점 처리·가격 변경 시 지급표 갱신은 미정이다. 표준 가격을 사용자 실제 결제액으로 표시하지 않는다.
UX 제안: “이번 주 TIG가 지급됐어요. 필요한 작업을 맡겨보세요.” 금액 확정 전 임의 수치를 기본값으로 넣지 않는다.
주간 발행은 계정·지급 주기 기준 중복 방지와 발행 근거를 원장에 기록한다. 요청/수행 거래량·지급 TIG 사용률·보상 수준·재방문을 통해 공급량을 검토하는 안을 제안한다. 남용 제한·지표 보존은 별도 결정한다.

## API 없는 플랜 식별과 지급 근거 — P-031

별도 유료 추론 API 호출 없이 공식 로컬 도구의 계정 metadata를 활용하는 경로를 검토한다. Tokenisgold 서버 통신과 공식 도구 자체의 네트워크 조회는 필요할 수 있다.
2026-09-09 [OpenAI 공식 App Server 문서](https://learn.chatgpt.com/docs/app-server): `account/read`는 ChatGPT 계정의 `planType`을 제공한다. 플랜 식별 경로는 확인했으나 모든 가격별 세부 등급을 구분한다는 보장은 없으며 설치 버전·반환값 검증이 필요하다.
[Claude Code CLI 문서](https://code.claude.com/docs/en/cli-usage)는 `claude auth status`의 JSON 인증 상태 출력을 설명한다. [인증 문서](https://code.claude.com/docs/en/authentication)는 구독/Console 등 인증 방식을 구분한다. 이 자료만으로 모든 플랜·가격별 세부 등급이 반환된다고 확정하지 않는다. 현재 환경에는 Claude CLI가 없어 실제 출력 검증은 하지 않았다.
두 경로에서 할인·세금·지역·결제 주기를 반영한 실제 개인 결제금액을 조회할 수 있다는 근거는 확인하지 못했다. 플랜명으로 실제 결제액을 단정하지 않는다.

로컬 조회 결과를 서버에 전달하는 것은 provider가 서버에 직접 증명한 결제 정보와 다르다. 값 변조·중복 연결·플랜 변경에 대한 지급 신뢰 기준은 WC-06·07에서 설계한다. 인증 credential은 수집하지 않는다.
미확인 플랜·세부 등급은 임의로 높은 등급에 매핑하지 않는다. 확인 실패 시 안내와 지급 처리는 미정이다. 두 서비스 동시 구독은 P-033에 따라 각 플랜의 주간 TIG를 합산한다.
UX 제안: “연결된 구독 플랜을 확인했어요. 해당 등급의 주간 TIG가 적용됩니다.” 실제 조회·등급 매핑 성공 후 표시한다.

## 복수 구독 처리 — P-033

P-033: Codex와 Claude Code의 지원 구독을 각각 연결·식별한 경우 각 플랜의 주간 TIG를 합산한다. 지급표 금액과 실제 플랜 식별 경로는 별도 확정·검증이 필요하다.
UX 예시: “연결된 두 구독의 주간 TIG가 합산됩니다.” 실제 플랜 확인과 지급표 매핑 성공 후 표시한다.
동일 구독의 기기별 중복 연결은 별도 구독으로 세지 않는다. 계정 식별·중복 방지의 구현 계약은 추가 설계한다. 서비스별 여러 계정·조직 구독의 대상 여부와 전체 상한은 미정이다.

## 지급 시점 — P-034

구독 확인 직후 첫 주간 TIG를 지급하고 이후 7일마다 자동 지급한다. 매주 수령 버튼을 요구하지 않는다.
UX 예시: “구독을 확인하고 첫 주 TIG를 지급했어요. 바로 작업을 맡겨보세요.”
추가 구독 연결 시 주기 정렬·플랜 변경·확인 불가·해지·누락 지급 처리는 미정이며 중복 지급을 허용한 결정이 아니다.

## 구현 전 합의할 점

P-041로 지급 산식을 확정했다. 원본 300/350 TIG 예시는 실제 요금표가 아니다. 가상의 월 20달러 플랜은 주 1,000 TIG이며 실제 플랜 가격을 검증했다는 뜻은 아니다.
P-042: 주간 지급분/수행 보상 모두 만료 없이 누적한다. P-043: 확인된 구독 종료 후 해당 구독의 다음 주간 지급을 중단하고 기존 잔액은 유지한다. 단순 조회 실패는 해지가 아니다.
P-029가 주간 공급을 허용한다. 구체적인 지급액·지급 대상과 주기 기준을 확정하고 발행 근거와 원장을 기록한다.
금액·수수료·자동 정산 조건을 구현자가 임의로 넣지 않는다.

## 결정 후 반영

관련 질문 ID에 확정 P-xxx를 연결하고, 동작·예외·완료 조건 및 영향받는 작업/계약을 갱신한다.

## 지급 예외 확정 — P-051

플랜 확인 실패 시 지급 대기·기존 잔액 사용, 복구 후 최근 미지급 1회분, 다음 주기 플랜 변경 반영, 제공사별 개인 구독 1개·조직 제외, 수수료 0을 확정했다. 각 구독의 최초 확인일 기준 7일 주기를 사용한다.
승인 원문과 범위는 [결정 묶음 2](20_decision_batch_two.md) 및 [확정 기록](00_confirmed.md)을 따른다. 이전 질문 표의 중복된 미정 표현보다 이 결정이 우선한다.
