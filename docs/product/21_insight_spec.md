# 요청·프로젝트별 인사이트 축적 설계 설계

P-040·056의 데이터 전략을 구체화한다. 수집·보존·동의·접근 경계는 [확정 데이터 정책](22_data_decisions.md)의 P-057~066을 따른다. 이벤트별 실제 필드/schema·삭제 구현은 명세 작업이다. 분석은 Tokenisgold에서 관측한 범위에 한정한다.

## 요청 분류

주분류: 프로젝트 신규 제작, 기능 추가, 버그 수정, 리팩터링, 테스트, 코드 리뷰, 문서화, 환경/배포 설정, 기타/미분류.
보조 태그: 언어/프레임워크, 프로젝트 유형(웹·모바일·라이브러리·자동화 등), 작업 규모, 요구 모델/추론, 완료 조건, 요청 보상.
AI 분류는 추정으로 표시하고 분류 버전·신뢰도·사용자 수정 이력을 둔다. 존재하지 않는 도구/모델명은 정규화 실패로 남긴다. 계정 또는 민감한 프로젝트 특성을 텍스트만으로 추정하지 않는다.

## 인사이트 후보와 정확한 의미

| 인사이트 | 관측/산식 제안 | 해석상 구분 |
| --- | --- | --- |
| 어떤 요청이 인기 있는가 | 기간별 분류의 게시 수/전체 게시 수, 고유 요청자 수, 열람/수락/제출 수 | 조회 관심·실제 수요·공급·완료는 별도 순위 |
| 어떤 요청이 수행자를 못 구하는가 | 미수락 비율·수락까지 중앙값/p90·조건별 대기 | 게시 후 경과 시간과 취소/만료 구분 |
| 어떤 프로젝트에서 많이 쓰는가 | 프로젝트별 게시/제출/승인/환불·활성 요청자·반복 게시 | 큰 프로젝트의 작업 수가 곧 사용자 수는 아님 |
| 프로젝트별 이용률 | 최근 7/30일 작업 게시 프로젝트 수 / 같은 기간 서비스 연결 상태의 관측 대상 프로젝트 수 | 전체 GitHub 프로젝트 또는 개발 활동 대비 시장 점유율이 아님 |
| 프로젝트 내 반복 이용 | 동일 프로젝트의 첫 요청 이후 7/30일 재요청 여부와 코호트 | 후속 관측 기간이 부족한 신규 프로젝트 분리 |
| 유형/스택별 채택 | 웹/모바일/라이브러리·언어/프레임워크별 활성 프로젝트/게시량 | 누락/추정 태그와 표본 수 표시 |
| 모델별 결과 | 작업 종류·난이도·환경별 검사 통과/직접 승인/환불·시간 분포 | 자동 지급은 품질 성공이 아니며 단순 순위는 인과 비교 아님 |
| TIG 순환 | 주간 발행·게시 예치·수행 획득·환불·획득 후 소비/보유 | 환불을 새 발행이나 성공 보상으로 세지 않음 |
| 자연어 UX 마찰 | 게시까지 질문 횟수·실패·포기·수락까지 단계 | AI 내부 추론 전문 수집이 필요하지 않음 |

프로젝트는 저장소 단위의 내부 project_id로 연결하고 GitHub 저장소 식별·이름 변경·fork 관계를 별도 기록하는 안이다. 같은 이름을 같은 프로젝트로 합치지 않는다. 외부 공개 리포트의 프로젝트명/소유자 공개는 승인하지 않았다.

## 원천 사건과 파생 분석을 함께 보존하는 구조 제안

원천 사건: event_id, task_id, submission_id, project_id, 제한된 사용자 식별자, 발생/수신 시각, event_type, 관측 출처, schema_version, 동의/보존 정책 참조.
파생 분석: insight_id, metric_key, 분석 기간/코호트, 분자·분모, 값·표본 수·누락률, 태그/쿼리/평가 버전, 생성 시각, 근거 사건 범위.
서술형 인사이트: 주장·근거 지표·표본/불확실성·생성 방식/버전·검토 상태. AI 해석을 사실 이벤트로 덮어쓰지 않는다. API 미도입 상태에서 서술형 생성 주체는 후속 설계이며 초기 집계는 SQL/규칙으로 계산할 수 있다.
같은 통계의 반복 계산을 새 성과로 세지 않고 계산 이력을 버전 관리한다. 원천 삭제 시 파생 결과/재계산/삭제 처리를 함께 정의한다.

## 수집 범위와 데이터 상품

“모든 인사이트”는 목적 있는 분류/분석을 확장할 수 있다는 의미다. 무제한 원문 수집·보존·판매 권한을 의미하지 않는다. 작업 요약과 승인된 metadata로 분석하고 키·전체 대화·숨겨진 파일을 통째로 수집하지 않는다.
원천/원문 보존기간·삭제·프로젝트 식별정보·사용자 동의·접근은 P-057~066으로 확정됐다. R09의 데이터 판매 후속 범위는 유지한다.

영어 대시보드 UX 예시: “Top request types · Most active project categories · Repeat usage · Unmatched demand”.
예시 설명: “Bug fixes account for 38% of posted tasks in the last 30 days.” 38%는 가상 수치이며 실제 기간·표본·분모가 있을 때만 표시한다.

## 승인 정책과 구현 명세 경계

P-057~066이 수집/분류/보존/삭제/선택 설정/접근/갱신의 제품 기준이다. 이 문서의 이전 미정/제안 표현보다 [확정 데이터 정책](22_data_decisions.md)이 우선한다. 개별 필드·집계 쿼리·삭제 작업/복원 재적용·권한 검증은 실제 구현 명세에서 검증한다.
