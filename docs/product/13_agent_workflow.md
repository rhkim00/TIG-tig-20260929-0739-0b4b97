# 자연어로 인계하고 수행하는 Tokenisgold

기준: P-011~024. 사용자가 제시한 중심 UX를 기록한 설계이며 구현 완료나 provider 허용 확인을 의미하지 않는다.
아래 화면 문구·세부 필드는 검토용 예시다. 실제 모델 ID·옵션·지원 OS·통신 방식은 별도 결정한다.

## 서비스의 이유

유찬은 일정 기간마다 갱신되는 AI 사용 가능량을 사람의 제한된 작업 시간처럼 본다.
쓰지 못한 기간별 사용 기회는 다음 시점에 그대로 저장되지 않는다는 문제의식에서 출발한다.
자기 사용량이 부족하면 TIG로 다른 사람에게 작업을 맡기고, 여유가 있으면 다른 사람의 작업으로 TIG를 얻는다.

주간 한도는 사용자가 제시한 동기/예시이며 모든 provider·플랜이 같은 주기나 정확한 token 수를 공개한다는 뜻이 아니다.
TIG는 완료된 작업의 대가로 받는 내부 포인트다. provider 토큰과의 고정 환율, 토큰 양도, 암호화폐는 이번 결정에 포함되지 않는다.

## 구성과 책임

| 구성 | 역할 |
| --- | --- |
| 사용자의 기존 공식 AI 도구 | 대화의 작업 맥락 이해, Tokenisgold 규칙 참조, 인계서/수행내역서 작성 |
| Tokenisgold CLI/연동 기능 | 승인된 명령 실행, Git 작업, task package 교환, 기기 상태/결과 동기화 |
| Tokenisgold 서버·DB | Task 저장, 권한/보상 예치, 가용성 기반 추천, 상태 전이, 검증 기록, TIG 정산 |
| Git/GitHub | 기준 코드·변경 이력·제출 결과와 관련 문서의 버전 관리 |
| 웹·알림 | 상태·추천·결과 확인과 필요한 승인. 알림 채널은 미정 |

Git은 코드/인계물의 버전 관리에 사용한다. 계정 잔액·claim 잠금·기기 토큰·민감한 원본 대화를 공개 repo에 넣는 것은 아니다.
상태·포인트의 실제 저장 설계는 ARCH 질문에서 확정한다.

## 1. 요청자: 하던 대화에서 작업 올리기

사용자 예시:

> 이걸 Tokenisgold에 올려줘. ChatGPT Astra로 ExtraHigh로 돌리고 싶고 보상은 1,000 TIG야.

요청자 AI의 목표 동작:

1. 현재 작업과 Tokenisgold 규칙을 읽는다. 규칙을 전달하는 skill/plugin/MCP/CLI 연동 방식은 미정이다.
2. 지금까지 한 일, 시도와 실패, 현재 코드 상태, 남은 작업, 제약, 완료 조건을 인계서로 정리한다.
3. 사용자가 지정한 모델/추론 요구와 보상을 구조화한다. 원문도 보존한다.
4. 기준 커밋과 필요한 미커밋 변경을 식별하고 승인된 방식으로 공유 가능한 작업 상태를 만든다.
5. 게시 조건·권한·TIG 잔액을 확인하고 Task를 게시한다. 모호한 부분이나 부족한 권한만 사용자에게 질문한다.

게시 완료 응답 예시:

> 작업을 올렸어요. 보상 1,000 TIG를 예치했습니다. 진행 상황은 이 링크에서 확인할 수 있어요.

이 응답은 실제 게시/예치가 성공한 경우에만 사용한다.
P-022: 작업·모델 조건·보상이 명확한 “올려줘” 발화를 게시·예치 승인으로 처리하고 추가 확인 없이 진행한다.
모호한 작업 범위, 보상 누락, 잔액·권한 부족, 지원 불가 모델 등은 해당 문제만 짧게 질문한다.
실패나 네트워크 재시도로 중복 게시·예치되지 않도록 서버에서 처리해야 한다. 명령 해석/멱등성의 실제 계약은 구현 전에 확정한다.

예외 UX: “보상은 몇 TIG로 할까요?” / “잔액이 700 TIG예요. 보상을 변경할까요?”
잔액 부족 시 임의로 보상을 줄이지 않는다. 게시 명령의 승인 범위는 그 작업과 지정한 보상에 한정한다.
Astra/ExtraHigh는 사용자가 제시한 요구 예시이며 검증된 모델 식별자나 실행 옵션이 아니다.
정확히 대응할 수 없으면 대체 모델/추론값을 몰래 고르지 않고 짧게 확인한다.

## 2. 수행자: 여유가 있다고 말하기

사용자 예시:

> 나 토큰 남았는데 TIG 벌 수 있는 작업 찾아줘.

수행자 AI/CLI의 목표 동작:

1. 선택한 공식 도구의 모델·플랜·실행 가능 상태와 제공 가능한 사용량 정보를 확인한다.
2. 필요한 정보만 Tokenisgold에 등록하고 추천을 요청한다.
3. 플랫폼은 Task의 모델/검증/환경 조건과 수행자의 역량·가용성을 비교한다. P-024에 따라 적합한 작업 하나를 먼저 추천한다.
4. 알림 또는 AI 응답에 수행할 작업과 보상을 보여준다. 웹/앱/이메일 중 채널은 아직 결정하지 않았다.

추천 응답 예시:

> 조건이 맞는 작업을 찾았어요. 로그인 세션 버그 수정 / 보상 1,000 TIG / 요청 모델 조건 충족. 시작할까요?

> Yes.

P-024: “다른 작업 보여줘”, “더 간단한 거”, “나중에”로 추천을 변경하거나 미룰 수 있다. 웹에서는 전체 마켓을 탐색할 수도 있다.
추천에는 작업 요약·보상·요청 범위·실제로 확인된 조건 일치 여부를 보여준다. 확인하지 않은 예상시간이나 완료 가능성을 단정하지 않는다.

“Yes”는 특정 작업을 수락하고 수행을 시작하는 의도다. 그 즉시 TIG를 지급한다는 의미가 아니다.
P-025에 따라 Yes는 해당 작업의 수행·합의된 검사·수행내역서 작성·Git 제출까지 포함한다. 정상 완료 시 제출 전 재확인을 요구하지 않는다.
한 번의 Yes가 다음 작업까지 계속 수락하는 권한이나 무기한 background 실행 권한은 아니다. 별도 연속 작업 정책은 FLOW-04에서 정한다.
사용자가 여러 곳에서 응답하거나 두 Worker가 동시에 수락할 때의 중복 claim은 서버 규칙으로 처리한다.

## 3. 수행: AI가 작업하고 제출 기록 작성

실행의 목표 흐름:

- 승인된 작업의 기준 코드·인계서·완료 조건을 준비한다.
- 약관상 허용이 확인된 방식으로 수행자의 공식 로컬 AI를 시작한다(P-010의 조건 유지).
- 코드 수정·합의된 검사 후 요청 사항과 실제 수행 사항을 연결하는 수행내역서를 작성한다.
- 코드와 수행내역서를 Git으로 버전 관리하고 추가 확인 없이 Tokenisgold에 제출한다(P-025).

시작 응답 예시:

> 시작했어요. 작업과 검사가 끝나면 수행내역서와 함께 제출할게요.

완료 응답 예시:

> 코드와 수행내역서를 제출했어요. 평가·승인 후 TIG가 정산됩니다.

서버에서 제출 성공을 확인한 뒤에만 완료 문구를 표시한다. 검사를 실행하지 못했거나 실패한 항목은 내역서에 그대로 기록한다.
권한 부족·사용 한도 소진·요청 범위 변경 등 진행을 막는 사유가 있으면 상태와 필요한 다음 행동을 안내한다. 실패를 완료로 표시하지 않는다.

> 작업에 필요한 저장소 접근 권한이 없어 중단했어요. 권한을 연결하면 이어서 진행할 수 있어요.

자동 제출은 요청자 저장소 병합이나 TIG 지급 승인을 포함하지 않는다. 직접 승인 정산은 P-026을, 검토 기한 48시간 미응답 자동 지급은 P-027을 따른다.
검사 실패 시 수정/중단/실패 제출 조건, 재시도 횟수와 재개 방식은 아직 미결정이다.

## 4. 플랫폼 평가·기록·정산

플랫폼이 완료 조건과 제출 내용을 평가하고, 난이도·소요시간·검증 결과 등 분석 가능한 데이터를 축적하는 방향을 확정한다.
P-026: 정상 정산은 플랫폼 검사 → 요청자 최종 승인 → TIG 지급 순서다. 테스트 통과만으로 즉시 지급하지 않는다.
P-027: 검토 기한 48시간 동안 요청자가 응답하지 않으면 예치된 작업 보상을 자동 지급한다. 운영자 검토로 넘기는 이전 제안은 대체됐다.
플랫폼은 변경 요약·검사 결과·미확인 항목을 보여주고 요청자는 승인 또는 결과 문제 접수를 한다.
P-028: 검토 중 수정 요청/분쟁 접수 시 예치 TIG를 요청자에게 전액 복구하고 거래를 종료한다. 수정 왕복·지급 보류·운영자 심사를 요구하지 않는다. 수행자 보상은 지급하지 않고 자동 지급 예약은 무효화한다. AI 사용량이 소진되어도 웹에서 검토·승인할 수 있어야 한다.
코드 병합은 별도 동작이다. 승인 후 정산 실패 시 성공으로 표시하지 않으며 중복 지급 방지·복구 계약은 WC-07에서 설계한다.
검사 실행 위치·통과 기준·요약 생성 및 AI 리뷰 주체는 미정이다. 별도 과금 provider API 미도입 원칙은 유지한다.
수행자의 보고 내용과 독립적으로 확인한 검사 결과는 출처를 구분한다. 기한 시작·알림·검사 실패·지급 후 신고의 세부 처리는 추가 결정한다.

결과 응답 예시:

> 로그인 오류 수정 결과가 도착했어요. 등록된 검사 8개가 통과했고, 확인하지 못한 항목이 1개 있어요.

화면: 변경 요약 / 검사 결과 / 미확인 항목 → “승인하고 1,000 TIG 지급” 또는 “문제 있어요 · TIG 돌려받기”(문구 제안).
검사 수치와 금액은 UX 예시이며 실제 확인된 결과와 해당 작업의 보상을 표시한다.
요청자의 “승인해줘” 또는 웹 승인 한 번으로 정상 정산을 진행하고 반복 확인하지 않는다.

정산 성공 시에만:

> 작업이 승인되어 1,000 TIG를 받았어요.

기한 만료 자동 지급 성공 시에는 직접 승인과 구분한다:

> 요청자가 48시간 동안 응답하지 않아 1,000 TIG가 자동 지급됐어요.

## 인계서·수행내역서의 데이터 후보

| 인계서 | 수행내역서 |
| --- | --- |
| 원래 요청, 현재 목표, 다음 작업 | 요청 조건별 수행 결과, 미완료 사항 |
| 이미 한 작업·시도·오류·근거 | 수정 내용·이유·영향 파일 |
| repo, base SHA, 선택한 작업 상태 | base/output SHA, 코드 diff, 제출 ID |
| 제약, 완료 조건·검사 방법 | 실제 검사 명령·결과·실패·미검증 사항 |
| 모델/추론 원문과 정규화한 요구 | 실제 도구/설정과 증거 수준 |
| 보상 TIG와 TaskSpec 버전 | 시작/종료 이벤트, 수정 횟수, 관련 실행 ID |

P-021: 최초 연결에서 선택한 프로젝트의 초안은 로컬에 자동 저장하고 “올려줘” 요청 시 게시에 필요한 내용만 서버로 보낸다.
전체 대화·비밀키·개인정보를 통째로 공개 Git에 넣지 않는다. 작업에 필요한 요약·코드만 선별한다.
미커밋 변경, gitignore 파일, 대용량 파일, 의존 환경을 어느 범위까지 인계할지는 FLOW-03에서 확정한다.
AI가 작업 맥락에 접근할 수 없는 도구/세션에서는 알고 있다고 가정하지 않고 필요한 최소 정보를 요청한다.

## 가용량과 데이터의 정확성

목표는 잔여량/플랜을 활용한 추천이다. 정확한 값이 실제로 조회되는지는 도구별 검증이 필요하다.
데이터는 조회값 / 사용자 선언 / 추정 / 알 수 없음으로 구분하고 출처·확인 시각·범위를 함께 기록한다.
한도는 token 수, 사용 비율, reset 시각 등 provider가 제공하는 단위를 유지한다. 같은 token 단위로 임의 환산하지 않는다.
“정확한 잔여량을 알 수 없음”을 “사용 불가” 또는 “무제한”으로 바꾸지 않는다. 자기 선언의 허용 여부는 FLOW-04에서 결정한다.

분석 후보: 요청 종류/언어, 사전 난이도 추정, claim 대기 시간, 실제 실행 시간, 사람의 검토 대기 시간,
수정 횟수, 검증/승인 결과, 보상 TIG, 확인 가능한 실행/사용량 지표.
AI의 난이도 추정은 정답 라벨이 아니다. 측정 시각·출처·평가 버전을 남긴다.
분석용 기록과 원문 데이터 보존·외부 제공·모델 학습은 별도다. 이번 요청으로 후자를 포괄 승인한 것으로 보지 않는다.

## 먼저 해결할 공백: 이미 사용량을 다 썼을 때

완전히 소진된 동일 모델이 더 이상 응답하지 못한다면, 그 모델에게 새 인계서를 작성하라고 요청하는 흐름도 막힐 수 있다.
P-019에서 작업 진행에 따른 인계 초안 자동 보존을 제품 요구사항으로 확정했다.
P-020은 소진 후에도 허용되는 보조 모델이 있다면 인계서 정리에 활용하는 조건부 경로다.
기록 저장과 LLM 요약을 분리하고, 모델 전환이 불가능할 때도 보존된 초안을 사용할 수 있도록 설계한다.
구체적 수집/요약/전환 정책과 공식 근거는 [사용량·초안 문서](14_usage_and_drafts.md)에 둔다.

UX 예시:

## 개발 영향

기존 TH-001~005만으로 전체 흐름을 구현할 수 있다고 보지 않는다.
범위 확정 후 별도 작업으로 대화 도구 연결, 작업 인계 schema, 가용성/추천, Yes 승인, 수행내역서,
평가/계측을 분해한다. 담당 배정과 기술 선택은 유찬이 결정한다.
과거 웹 양식 중심 UX는 이번 자연어 흐름의 상태 확인·수정·보조 경로로 조정한다.

## 데이터 정책 확정 — P-057~066

수집/프로젝트 식별/분류·자료 보존/분석 보존·30일 오류 로그/백업·선택 분석 기본 꺼짐·내보내기/삭제·인사이트 권한/공개 집계 기준·일일 집계를 확정했다. [확정 데이터 정책](22_data_decisions.md)을 최신 기준으로 적용한다. 이전의 보존/동의 전면 미정 표현은 이 결정으로 대체하며 정책 문구·필드·권한/삭제의 실제 구현 검증은 남아 있다.

## P-067 요청자 흐름 우선 구현

기존 AI의 명세 작성 → TIG prepare의 request.md·선택 코드 preview → 승인 범위 내 publish의 별도 Git 요청 커밋 및 플랫폼 게시를 먼저 구현한다. 원본 작업 상태 보존, 새 공개 공유/명세 변경 승인 구분, 고정 커밋과 플랫폼 작업 일치를 따른다. [실행 계약](../contracts/requester_git.md)과 [사용법](../REQUESTER_QUICKSTART.md)을 참조한다. 설치 안내가 자동 인계 요약 hook이나 실제 수행자 AI 실행의 완료를 뜻하지 않는다.

## P-068 반영 — tig 단독 실행

새 기본 진입은 `tig` → 폴더/자연어 → 최초 연결 안내 → 공식 로컬 Codex 명세 → 공유 조건 한 번 확인 → 게시다. 기존 AI가 직접 고급 명령을 호출하는 경로도 유지한다. CLI 0.4.0은 최초 로그인/프로젝트 전달 저장소를 기억하고, 새 파일 공개 선택과 최종 공유 목록을 보여준다. 대화형 초안은 이전 AI 대화를 자동 상속하지 않는다. 수행자 모델 조건과 요청 명세 작성 모델을 구분한다. [구현 사용법](../REQUESTER_QUICKSTART.md).
