# 최종 명세를 위한 결정 묶음 2 — 승인/보완 기록

관련: [남은 결정 감사](19_readiness_audit.md). 최초 작성 시에는 제안이었고, 후속 답변의 R08 보완 및 나머지 동의를 아래 승인 기록으로 반영했다. 구현 착수/완료를 뜻하지 않는다.
최신 답변으로 R01~R07·R09·R10은 P-047~055로 승인됐다. R08은 P-056의 인사이트 방향과 P-057~066의 데이터 정책으로 확정됐다. 아래 추천 원문은 이력이며 최신 승인 기록이 우선한다. 숫자는 검증된 최적값이라는 뜻이 아니다.

## R01 검사와 48시간 시작점

추천: 합의된 필수 검사를 마치고 코드·수행내역서·검사 결과가 웹에서 열리는 시점부터 48시간을 센다. 이메일 열람을 기산점으로 삼지 않는다.
필수 검사 실패/실행 불가 시 제출 전 실행 기한 내 수정·재검사하고, 끝내 충족하지 못하면 전액 환불·종료한다. 테스트 없는 프로젝트는 게시 전에 검사 가능한 완료 기준을 합의한다.
수행자 AI가 보고서를 작성하고 플랫폼은 구조·증거 출처를 확인한다. 로컬 검사와 독립 CI 결과를 구분하고 별도 유료 평가 AI는 도입하지 않는다. 독립 실행/격리 방식은 사실 검증 후 계약화한다.
UX: “Ready for review. Auto-payment in 48 hours.”

## R02 수락과 작업 기한

추천: 작업당 수행자 1명, 수행자당 동시 작업 1개. 수락 후 10분 안에 실행 시작, 작업 전체 기한은 게시 시 명시하고 기본 24시간으로 한다.
24시간 내 수행하기 어려운 큰 프로젝트는 단계/기한을 게시 전에 정한다. 시작하지 못한 수락은 해제해 재추천한다. 수락 전 요청자는 취소·전액 복구할 수 있다. 수락 후 범위 변경/취소 세부는 R04와 상태 계약에 연결한다.
UX: “One task is running. You can accept another after it finishes.”

## R03 중단과 재배정

추천: 토큰 소진/오프라인 시 작업을 저장하고 30분간 재개 기회를 준다. 이후 실행 권한을 회수하고 다른 수행자에게 1회 재추천한다. 전체 게시 기한은 연장하지 않으며 완료되지 않으면 전액 환불·종료한다.
예치금은 유지하고 추가 보상을 청구하지 않는다. 미완료 수행자에게 부분 보상은 지급하지 않는 안이다. 이전 실행 권한을 폐기하고 늦은 제출을 거부하는 계약과 로컬 중단 가능성 검증이 필요하다. 안전하게 권한 회수/중단을 보장할 수 없는 경로를 구현 가능으로 가정하지 않는다.
UX: “Your worker disconnected. We’re finding a replacement at no extra TIG.”

## R04 프로젝트 범위와 결과 반영

추천: 프로젝트 제작은 허용하되 AI가 범위·완료 조건·기한을 먼저 구조화한다. 명확한 게시 명령은 P-022대로 처리하고 모호한 범위만 보충한다. 여러 거래로 분할하거나 추가 예치할 때는 요청자의 승인을 받는다.
수락 후 요구사항/보상은 고정한다. 추가 요구는 새 작업이다. 제출은 PR로 하고 요청자의 별도 “Apply changes”로 병합한다. 충돌 시 자동 덮어쓰기 대신 미반영 상태와 해결 내용을 안내한다. 승인/자동 지급만으로 병합하지 않는다.
UX: “The project is ready. Review the changes or apply them.”

## R05 주간 TIG 예외

추천: 구독 확인 불가 시 신규/다음 주 지급을 대기시키되 기존 TIG 사용은 허용한다. 플랜 확인이 복구되면 최근 미지급 1회분만 지급하고 오래된 주차는 소급 적립하지 않는다.
플랜 변경은 다음 지급에 반영한다. 두 서비스는 각각 최초 확인일 기준 7일 주기를 갖고 같은 주의 지급 합계를 보여준다. 같은 제공사에서는 사용자당 개인 구독 1개만 인정하며 조직 구독은 베타 대상에서 제외한다.
베타 지급/거래 수수료는 0, 별도 합산 상한은 두 개인 구독의 산식 합계로 한다. 실제 플랜 증명·중복 식별 가능한지는 별도 검증이다.
UX: “We couldn’t verify your plan. Your existing TIG is still available.”

## R06 로컬 보호와 공유 범위

추천: 선택한 프로젝트의 추적 파일·필요한 미커밋 코드 변경·선별 인계 요약만 전달한다. 비밀키/환경파일·전체 대화·프로젝트 밖 파일은 자동 전송하지 않는다. 추가 미추적 파일은 포함 목록을 확인받는다.
수행은 별도 작업 공간에서 진행한다. GPU 학습·관리자 권한·홈 폴더 탐색·임의 외부 전송을 제한하고 CPU/RAM/디스크 예산을 실행 전에 적용한다. 수치는 OS별 실험 뒤 제시하며 현 단계에서 격리 완료로 간주하지 않는다.
공식 AI 연결에 필요한 인증/네트워크와 프로젝트 코드 실행의 권한을 분리 설계한다. 요청 모델/추론이 지원되지 않으면 임의 변경하지 않고 가능한 대안을 제시한다.
UX: “This task runs in an isolated workspace. Your other projects stay outside its scope.” 실제 검증된 환경에서만 표시한다.

## R07 초안·보조 모델·사용량 알림

추천: 파일/작업 이벤트는 로컬에 증분 저장한다. 인계 요약은 AI 응답 완료 시 갱신하되 별도 요약 호출은 최대 10분에 한 번으로 제한하고 변경이 없으면 실행하지 않는다.
보조 모델 사용은 처음 설정에서 선택하게 하고 기본은 꺼짐으로 한다. 사용 불가 시 저장된 초안으로 인계한다. 가용성 조회와 실행을 허용 범위 내에서만 한다.
공식 한도 중 하나라도 사용률 80% 이상이면 부족 안내, 모든 필수 확인 가능 한도가 30% 이하일 때 여유 안내를 제안한다. 6시간 내 같은 알림은 반복하지 않는다. unknown을 여유로 간주하지 않는다.
UX: “You’re nearing your limit. Your handoff draft is saved.”

## R08 데이터 수집과 보존

추천: 작업 종류·요구/관측 모델·추론 설정·시간·매칭·검사 근거·지급/환불·재방문 이벤트를 구조화해 축적한다. 결측·선언·실제 관측을 구분한다.
보존 초기안: 디버깅 원문 로그는 마스킹 후 30일, 식별 가능한 분석 이벤트는 1년, 개인을 식별하지 않도록 검토한 집계는 장기 보존한다. 서비스 내 작업 산출물과 정산 원장은 디버깅 로그와 구분하고 운영/삭제 정책을 별도 명세한다. 위 기간은 법률상 의무라는 주장이 아닌 제품 제안이다.
원문 코드/대화의 판매·외부 연구 제공은 베타에서 하지 않는다. 후속으로 권리·동의·제공 대상을 검토한다. 직접 승인·자동 지급·환불을 품질 성공/실패와 구분한다.
UX: “See what we collect and manage your data in Settings.”

## R09 기술·범위·예산

추천: 웹·서버·CLI는 TypeScript를 공통 언어로 하고 PostgreSQL로 작업/원장 상태를 관리한다. 패키지·버전·호스팅 업체는 호환 검증 및 견적 후 구체화한다. 관련 공식 자료: [TypeScript](https://www.typescriptlang.org/docs/), [PostgreSQL 거래 격리](https://www.postgresql.org/docs/current/transaction-iso.html). 기술 선택은 제안이며 DB 사용 자체가 중복 정산을 해결하는 것은 아니다.
월 인프라 예산 상한은 100달러로 제안한다. 실제 견적/충족 가능성 확인 전 구매·배포를 승인한 것으로 보지 않는다. 초과 예상 시 범위/예산안을 제시한다.
Windows 네이티브를 병행 검증하되 실패하면 macOS/Linux/WSL2 베타를 먼저 낸다. 핵심 추천·마켓·잔액·거래 이력·집계는 포함하고 광고·고급 평판·모바일 앱·private 저장소·데이터 판매는 후속으로 둔다.
UX: “Choose your setup: macOS, Linux, or Windows with WSL2.” Windows 네이티브는 실제 검증 통과 후 추가한다.

## R10 역할·운영·출시

추천: 유찬은 서버/CLI/AI 연동/정산, 륜호는 영어 웹/온보딩/알림/설치 UX를 맡고 서로 PR 리뷰한다. 유찬이 최종 병합·출시한다.
Day 1은 정책 명세 승인 후 기술 검증을 시작하는 날로 정의한다. 당장 달력 날짜를 임의로 넣지 않는다. Day 9부터 새 기능을 멈추고 통합·복구 검증에 집중한다.
일반 수정/분쟁은 P-028 환불·종료를 유지한다. 지급 이후 신고와 반복 남용 의심은 운영자가 검토하되 자동 TIG 회수/제재를 하지 않는다. 문의는 이메일 한 채널로 시작한다.
매일 DB 백업, 출시 전 복구 리허설, 외부 계정 전체 거래·지원 OS/도구·중복 지급/환불·권한 경계 검증을 필수로 제안한다. provider 허용/실제 검증 공백이 남으면 관련 기능의 출시 여부를 유찬이 별도 판단한다.
UX: “Need help? Contact support.”

## 승인 이후 남는 작성 작업

승인된 정책의 API/상태/원장/이벤트 명세와 실행 검증을 작성한다. 수치 실험이 필요한 자원 상한, 실제 지원 플랜 가격표, 세부 권한·원장 보존/삭제·호스팅 견적은 근거를 갖춰 제시한다. 이 문서 승인만으로 미검증 사실이 확정되거나 모든 구현 계약이 완성되는 것은 아니다.

R08의 최신 승인 보존/삭제/동의/접근 규칙은 [확정 데이터 정책](22_data_decisions.md)이 우선한다. 위 R08 초기 제안의 미정 표현을 현재 상태로 해석하지 않는다.
