# Requester Git publication — schema 1 / CLI 0.3.0

P-067: the user's existing AI writes the request from its current context. TIG provides instructions, validates the package, publishes a pinned Git snapshot and registers the task. This flow does not execute another user's AI.

## CLI contract

1. `tig connect --origin <website>` pairs a device to Tokenisgold. GitHub authentication remains in the user's `gh` installation (`gh auth login`), separate from TIG pairing. No GitHub/provider token is copied into the task or TIG config.
2. `tig init --project <local-git-project>` records the project's connection (server, account). No repository is chosen: every published request becomes a new **public** repository under the requester's GitHub account (`<login>/<folder>-tig-<YYYYMMDD-HHMM>-<id prefix>`), created only at publish time, never by init or prepare. It never changes private repository visibility. The local project currently needs at least one Git commit and a configured commit name/email.
3. Optional `--install-instructions` writes `TOKENISGOLD.md` and appends a reference block to AGENTS.md and CLAUDE.md, preserving existing rules. Existing differing TOKENISGOLD.md or symlink destinations are rejected. Without the option, tell the AI to read `tig instructions` explicitly. Existing AI sessions may need to reread the files.
4. `tig request prepare --project <path> --spec <json> [--include <selected-untracked-paths...>]` uses the shared `requestInput` schema to produce a frozen local preview. The AI writes the JSON outside the source project. Fields: title, requestCategory, originalRequest, context, completedWork, scope, constraints, setupSteps, testSteps, acceptanceChecks, aiRequirement, rewardTig, executionDeadlineAt. Missing requirements are errors, not invented defaults. Model/effort are requested values with declared/client-observed/unknown provenance, never server-verified support.
5. `tig request show <id>` returns the preview, selected/excluded file names, request.md path, repository/branch/commit, reward/deadline and SHA-256 preview digest. Full contents can be reviewed in the local snapshot directory. Protected files are omitted; omitted required files must be resolved before posting. No public side effects during prepare/show.
6. `tig request publish <id> --approve <digest> --yes` authorizes the **exact public snapshot and its reward**. The existing AI may use an already explicit user post instruction within its approved scope (P-022); repeated human confirmation is not required when sharing scope/reward are already authorized. Changed content, new public visibility or missing terms cannot borrow approval from an earlier request.

## Git layout and invariants

Each request's repository is created empty at publish and the request commit is pushed as its `main` branch, so the repository landing page is `request.md` and the project as the requester had it. The commit is a parentless snapshot: original private Git history is never copied. With layout "tree" (the default, see below) its root is the requester's whole working tree plus the two documents; with layout "bundle" its root contains `request.md`, `request.json`, and `code/` with the selected source snapshot. `code/` may be absent for a new-project request (P-036). Requests published by an earlier tig live as `tig/requests/<UUID>` branches in a per-project repository; the server and the worker accept both branch shapes (`TaskSpec.gitRequest.branch` is `main` or `tig/requests/<id>`). The original source HEAD, index, branch and worktree are untouched by prepare/publish.

Selected tracked files include their current uncommitted contents; additional untracked files require explicit `--include`. Missing/deleted files are absent from the full snapshot. Paths/known secrets/symlinks/binary files are excluded. Limit: 98 source files plus two documents, 200 KB per text file and 1 MB total. Size truncation causes prepare to fail; other exclusions are shown. This conservative scanner does not prove all code safe to publish. Hidden paths are excluded under the existing upload policy; projects requiring them need scope/packaging work before this development flow can run their tests. Source executable permissions are not copied; generated files are regular text files (Git mode 100644). **위 두 문단은 `layout: "bundle"`(`TIG_REQUEST_LAYOUT=bundle`)에만 해당하며 바이트·검증 규칙은 그대로 유지된다.**

### layout "tree" (CLI 0.5 기본)

`tig`와 `tig request prepare`의 기본 레이아웃이다. `request.json`에 `layout: "tree"`가 기록되고(bundle은 필드 없음), 요청 저장소의 `main`은 부모 없는 커밋 하나로 그 루트가 **요청자의 작업 상태 전체**다: 추적 파일 전부(HEAD 트리 + 미커밋 변경, `.gitignore` 준수, 실행 권한 100755 유지, 바이너리 허용)에 **미추적 파일 전부**(사용자 결정 2026-09-22 "현재 작업하는 repo의 파일들 다 올라가면 돼": 이름·폴더·크기 규칙 없음, 예전의 데이터 확장자·미추적 폴더·1 MB·300개/20 MB 예산 규칙과 `untrackedSkipReason`은 제거)를 더하고 루트에 `request.md`·`request.json`을 넣으며 `code/` 접두는 없다. 모든 미추적 파일을 읽어 비밀 검사를 하므로 미추적 파일이 수만 개인 저장소는 그만큼 시간이 걸린다. 요약 첫 줄의 `New (untracked) by folder: …`은 `(every new file travels except protected paths and files holding a secret; ignored files never do)`로 끝난다; `Left out, not in git` 줄은 없어졌고 스키마의 `skippedCount`/`skippedDirs`는 예전 plan 호환을 위해 남아 항상 0/[]이다. 제외(사유가 `excluded`에 남고 요약에 표시): `protectedPath`(files.ts — `.env*`(예시 파일 제외), `.git`, `.github/workflows/**`("CI would run"), `.mcp.json`, `.claude/settings.local.json`, `.codex`, `.aws`, `.ssh`, `.kube`, `.netrc`, `credentials`, `secrets`, `id_*`, `auth.json`, `kubeconfig`, `node_modules`, `venv`, `.venv`, `__pycache__`("dependencies"), `.pem/.key/.p12/.pfx/.keystore/.jks/.tfstate/.tfvars/.log` 등), `SECRET_SCAN_LIMIT`(현재 10 MB) 이하 파일 중 `containsSecretBytes`에 걸리는 파일("secret"; 아래 **비밀 게이트** 참고, **바이트**로 검사하므로 CP949·UTF-16 소스도 걸린다), 심볼릭 링크, 중첩 저장소 디렉터리, `filter=lfs` 속성 경로("git-lfs"), 워킹트리에서 지워진 파일("deleted"), 100 MB 초과 파일("too-large-for-github"). 추적 파일 제외는 `trackedExcluded`/`trackedExcludedCount`로 요약에 실려 `Tracked but left out: …` 줄이 된다. 이 수집 단계 검사는 **화면에 사유를 적기 위한 것**이고 보증은 아래 게이트가 한다. 총합 1 GB 초과는 `TREE_TOO_LARGE`로 중단한다. 프로젝트에 이미 `request.md`/`request.json`이 있으면 `REQUEST_DOC_CONFLICT`. merge/rebase/cherry-pick 진행 중·unmerged 경로(`MERGE_IN_PROGRESS`), sparse checkout·skip-worktree(`SPARSE_CHECKOUT_UNSUPPORTED`), partial clone(`PARTIAL_CLONE_UNSUPPORTED`)은 거부한다. shallow clone은 허용한다.

**제외 목록의 자리 배분(`LIST_CAP`)**: 저장되는 `excluded`는 500개까지인데, 실제 저장소에서는 보호 경로(`node_modules/`, `.venv/`) 수천 개가 알파벳 순으로 먼저 들어와 그 500칸을 채울 수 있다. 그래서 `collect()`는 한 목록에 섞지 않고 세 갈래로 모은다 — 추적 파일 제외(`trackedOut`, 200칸), 요청자가 직접 관계된 제외(`chosenOut`: 거절한 새 파일, 파일을 읽어서 결정된 secret/unreadable/symlink/git-lfs/nested-repository/too-large-for-github, 200칸), 대량 보호 경로(`bulkOut`, 남는 칸). 합쳐서 발견 순서(`seq`)로 되돌리므로 넘칠 일이 없을 때의 목록은 예전과 글자 그대로 같고, 넘칠 때도 요청자가 손쓸 수 있는 제외는 절대 밀려나지 않는다. 개수(`excludedCount`)는 잘린 것과 무관하게 항상 전수다. 추적 파일 제외는 따로 `trackedExcluded`(경로+사유, 상위 50개)와 `trackedExcludedCount`(전수)로도 요약에 실려 화면의 `Tracked but left out: src/db.ts (secret), assets/model.bin (git-lfs) … — git tracks these files and they are still not in the branch.` 줄이 된다.

**새 파일에 대한 요청자의 답(P-052 동의)**: `tig`의 대화 흐름은 새 파일에 대해 묻지 않고 전부 올린다. 수동 경로 `tig request prepare --include <paths...>`가 답을 줄 때만 `approvedUntracked: string[] | undefined`가 `prepareRequest` → `prepareTree` → `buildRequestTree` → `collect(ctx, docs, selection)`까지 전달된다(`Selection.untracked`). `undefined`는 "묻지 않았다"라서 모든 새 파일이 올라가고, 배열은 요청자의 답이라 **그 경로들만** 올라간다(`[]`이면 새 파일이 하나도 올라가지 않는다). 답은 좁히기만 하고 넓히지 못하며, 추적 파일은 이 답으로 빠지지 않는다. 빠진 경로는 `REFUSED_REASON`("you chose not to share this new file")으로 `excluded`에 남고, `refusedPaths`(전수)는 `immutable.untrackedNotShared`에 저장되며, `verifyRequestTree`가 게시 직전 트리에 그 경로가 하나라도 있으면 push를 막는다. 요약에는 `Kept private at your request: 1 new file you did not include — notes.md. It is not in the branch.`로 나온다.

트리는 `apps/cli/src/request-tree.ts`가 임시 index(`GIT_INDEX_FILE=<requestDir>/index`)와 임시 객체 디렉터리(`GIT_OBJECT_DIRECTORY=<requestDir>/objects`, 원본 objects는 `GIT_ALTERNATE_OBJECT_DIRECTORIES`로 읽기만)에서 `read-tree HEAD` → `update-index --add --stdin -z`(경로를 그대로 넘기므로 `pages/[id].tsx` 같은 이름도 glob 해석 없음) → HEAD에만 있던 경로 `--force-remove` → `hash-object -w` + `update-index --cacheinfo 100644`로 문서 추가 → `write-tree` → `commit-tree`(`-p` 없음)로 만든다. 로컬 연산은 `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1`에 `core.hooksPath`(빈 디렉터리)·`core.fsmonitor=false`·`core.safecrlf=false`·`core.splitIndex=false`·`commit.gpgsign=false`를 붙여 실행하고 원본 저장소의 `.git/config`(autocrlf, filemode)는 그대로 적용된다. ref는 `<requestDir>/push.git`(bare, alternates = 임시 objects + 원본 objects)에만 만들고 push도 거기서 한다. 원본 `.git`의 index·HEAD·refs·objects는 바이트 단위로 불변이다(테스트가 `.git` 전체 해시로 확인). 게시 전 검증은 push.git에서 부모 0개, 루트의 두 문서가 100644 blob이며 sha1이 artifact 내용과 같고, 트리 전체에 `protectedPath` 경로가 없음을 보고, **그다음 같은 커밋에 비밀 게이트를 돌린다**(아래). push는 30분 제한, `GIT_TERMINAL_PROMPT=0`, 글로벌 `url.*.insteadOf`가 `https://github.com/`를 재작성할 때만 `GIT_CONFIG_GLOBAL=/dev/null`(시스템 config는 항상 유지).

### 비밀 게이트(secret gate, `apps/cli/src/secret-gate.ts`)

"비밀처럼 보이는 것은 공개 브랜치에 가지 않는다"는 규칙은 **한 곳**에서만 보증한다. 파일별 스캔이 네 군데 흩어져 각자 다른 것을 읽던 구조에서 두 차례 연속으로 구멍이 났기 때문이다 — 요청자 쪽은 워킹트리 파일을 읽는데 index는 `git status`가 "수정 없음"이라고 부르는 추적 경로에 대해 **HEAD의 blob**을 발행했고(`git update-index --assume-unchanged`로 재현; preflight가 막는 것은 형제 비트인 skip-worktree뿐이다), 수행자 쪽은 UTF-8로 디코딩되는 blob만 검사하면서 나머지에도 `scanned: true`를 기록했다(CP949 한글 소스, UTF-16 파일).

게이트는 **발행될 커밋 자체**를 읽는다: `git ls-tree -r --long <commit>`로 그 커밋이 가진 blob을 모두 열거하고, 각 blob을 `git cat-file`(필터 없음 = `git push`가 보내는 바이트 그대로)로 1 MiB 창 + 64 KiB 겹침으로 흘려 읽으며 매칭한다. 패턴(`SECRET_PATTERNS`, packages/contracts/src/files.ts)은 전부 ASCII라 **디코딩이 필요 없다**: 바이트를 latin1로 그대로 보고(모든 ASCII 바이트는 제자리, 나머지는 non-word 문자), NUL을 제거한 두 번째 패스로 UTF-16/UTF-32까지 본다. 기본값에 크기 상한은 없다(10 MB 넘는 파일도 끝까지 읽는다). 호출 지점은 두 곳뿐이고 둘 다 `scanRequestCommit`(request-tree.ts)을 쓴다:

1. `buildRequestTree` — 커밋을 만든 직후. 걸리면 `SECRET_IN_REQUEST_TREE`로 준비가 중단되므로 요청자는 승인 화면 전에 알게 된다.
2. `verifyLocalSnapshot`(publishRequest의 push 직전 검증) — layout tree와 bundle **둘 다**. 통과하지 못한 커밋은 push되지 않는다. 메시지는 파일과 **패턴 분류 이름**만 말하고(비밀 자체는 절대 싣지 않는다) "아무것도 push되지 않았고 프로젝트는 그대로다, 비밀을 지우고 tig를 다시 실행하라"로 끝난다.

건너뛰는 것은 두 가지뿐이다. (a) 루트의 `request.md`/`request.json` — tig가 envelope에서 직접 쓰고 `containsSecret`으로 검사한 바이트이며, 바로 위 검증이 발행 blob이 그 바이트와 동일함을 sha1로 확인한다. (b) 첫 바이트가 알려진 바이너리 컨테이너(PNG/JPEG/GIF/PDF/ZIP/gzip/ELF/Mach-O/wasm/mp4)인 blob — 압축·엔트로피 코딩된 페이로드 안에서는 키의 ASCII가 ASCII로 남지 않기 때문이다. 이건 알려진 사각지대이므로 **침묵하지 않고 공시한다**: 게이트가 돌려준 목록 그대로 `unscannedCount`/`unscannedBytes`/`unscannedPaths`(경로·사유·크기, 50개까지)에 담겨 요약 `Tree:` 줄 끝에 `· 2 files the secret gate could not examine (binary format): assets/logo.png, assets/data.gz`로 나온다. 숫자는 게이트가 실제로 건너뛴 blob 수이며, 그 밖의 blob은 마지막 바이트까지 읽힌 것이다(P-052). 잡지 못하는 것: EBCDIC·UTF-7·base64 같은 변환 인코딩, 컨테이너 내부, 패턴 표에 없는 형식(고엔트로피 비밀번호 등), 경로 이름(그건 `protectedPathReason`의 몫).

서버에 보내는 artifact는 `request.json`·`request.md` 두 파일뿐이고 `baseCommit`은 요청 커밋, `gitRequest.sourceCommit`은 원본 HEAD다. 서버는 `layout`이 `tree`면 루트 트리(비재귀)에서 두 문서 blob만 대조한다([task_api.md](task_api.md)). 승인 digest는 `immutable`(commit sha, `tree` 요약, `destination`, 저장소 이름 포함)의 sha256이므로 파일 하나만 바뀌어도 새 준비·새 승인이 필요하다. 저장소 id와 플랫폼 project id는 게시 시점에 생기므로 `plan.json`(`repositoryId`, `projectId`)에 digest 밖으로 기록된다. `capture()`는 준비 중 프로젝트가 바뀌었는지 확인하는 manifest에만 쓰이고 게시 트리와 무관하다.

**목적지**: 요청마다 새 공개 저장소다(사용자 결정 2026-09-22 "무조건 요청할 때마다 새로운 git"). `prepareRequest`가 `gh api user`의 login과 프로젝트 폴더 이름으로 `requestRepositoryName(login, root, id)` = `<login>/<slug>-tig-<YYYYMMDD-HHMM>-<id 앞 6자>`를 정해 `immutable.repository`와 request.md의 `Delivery repository:`에 적고(`destination:"new"`, 브랜치 `main`), `publishRequest`가 지갑 잔액·로컬 스냅샷·비밀 게이트 검사를 **모두 통과한 뒤** `gh repo create <name> --public`(README 없음)으로 만들고 `main`으로 push한 다음 `POST /v1/projects`로 그 저장소를 플랫폼 project로 등록해 그 `projectId`로 task를 게시한다. 거부된 요청은 빈 공개 저장소를 남기지 않는다. 재시도는 `plan.repositoryId`/`plan.projectId`를 재사용하고, 생성이 이미 됐는데 기록 전에 죽은 경우는 `gh repo create` 실패를 무시하고 `gh api repos/<name>`으로 같은 이름·공개·push 가능을 확인한다. 서버 `verifyGitRequest`는 `gitRequest.branch`가 `main` 또는 `tig/requests/<envelope.id>`인지 확인한다. 결과: 요청 N건 = 공개 저장소 N개 + 플랫폼 project N개(인사이트·집계의 project 단위 의미가 "요청 1개"로 바뀐다), 수행자 계정에는 fork N개. 예전 tig의 프로젝트별 요청 저장소(`destination:"origin"|"delivery"`, `immutable.repositoryId`/`projectId` 보유)로 준비된 plan은 그 저장소로 게시된다. `tig setup`은 서버·프로젝트 연결만 다시 안내한다.

Git config for hooks, author identity, line endings and signing is set only inside the newly generated delivery repository. Source repository hooks are not bypassed or modified. GitHub credentials are used by gh's credential helper for the fixed HTTPS GitHub destination; subprocess credential/error output is not forwarded. No source commands, setup scripts or request instructions are executed while preparing/publishing.

## Server contract

Existing artifact/task endpoints are reused. `TaskSpec.gitRequest` is optional for compatibility and contains `{repository, branch, sourceCommit, requestPath: "request.md"}`. `baseCommit` is the published **delivery commit**, while sourceCommit is provenance for the original project state. Task JSONB stores the metadata; no migration required.

On a Git-backed post, the server checks artifact ownership, request.json schema, deterministic request.md rendering, task fields/reward/original approval agreement, repository identity and artifact manifest. It obtains the pinned Git commit/tree from GitHub and rejects parent history, truncated trees, extra/missing/different blobs, symlinks/submodules or unexpected modes. Only then does the existing transaction create the task/escrow. `requestUrl` in TaskView is derived from validated repository and baseCommit. CLI receipt includes taskId, taskUrl (`/?task=<id>`) and requestUrl. Web deep links require normal sign-in and task access.

GitHub API references: [Git trees](https://docs.github.com/en/rest/git/trees), [repository creation](https://cli.github.com/manual/gh_repo_create). GitHub/API transport verification is distinct from request author claims and from AI execution/model proof.

## Retry and failure behavior

- Local plans bind the exact content, commit, target GitHub repository ID, Tokenisgold user and server to the approved digest. Changed account/server or plan content is rejected.
- Insufficient balance is checked before the first push; authoritative escrow still runs transactionally on the server.
- A local exclusive publication lock blocks concurrent processes for one ID. After a process crash, inspect that no publisher remains before removing only the indicated lock file.
- Push is non-forced and retryable to the same branch/commit. A lost push response may mean Git is already public. Never claim an error rolled public Git back.
- Pushed/artifact/receipt checkpoints are saved locally. Stable artifact/task idempotency keys prevent duplicate tasks and escrow. On network/verification failure repeat the same ID, not prepare a new one. A lost successful task response replays the existing server result even if GitHub is later unavailable.
- GitHub publication and PostgreSQL are separate systems: there is no cross-system atomic rollback. The preview/receipt reports Git publication separately. A new request is needed to change a prepared snapshot/deadline; it requires new approval.

## Explicit limits

This release is requester publication, not actual worker execution, matching or model support verification. It does not expose the private Tokenisgold development repo, configure live OAuth, issue trusted subscription entitlements, install an autonomous AI agent or deploy the public beta. Public repository creation/upload needs user authorization. External GitHub write verification and native OS support must be reported separately from local bare-remote/HTTP/DB test evidence.

## CLI 0.4.0 대화형 호출

`tig`와 `tig setup`은 동일한 init/prepare/show/publish 함수를 내부에서 호출한다. 서버 task/artifact 계약은 그대로다. wizard는 로컬 AI를 부르지 않는다(사용자 결정 2026-09-22): 후보 폴더를 확인받고(`chooseProjectFolder`), 작업·도구·모델·추론 수준·TIG를 한 답에서 읽어(`request-terms.ts` `parseRequestTerms`; 끝에 붙은 조건절만 잘라내고 문장 안의 조건은 문장을 그대로 둔다) 빠진 항목만 묻고(`askWorkerAi`, `collectReward`, `askAcceptance` — 추천·산정 없음, `recommend.ts`/`reward.ts` 삭제), 완료 기준을 요청자에게 받아(Enter=요청 문장의 문장 단위), 프로젝트 사실(`request-facts.ts`: 브랜치·HEAD·변경 수·최상위 구조·최근 커밋 제목 5개·`package.json`/`requirements.txt`/`pyproject.toml`/`Cargo.toml`/`go.mod`/`Gemfile`/`Makefile`에서 감지한 설치·테스트 명령, 키워드 카테고리)로 `buildRequestInput`이 `requestInput`을 만든다. 리뷰 화면의 `no`는 지시를 `scope` 끝에 이어 붙여(`session.revision`) 다시 준비한다. 사용자에게 digest/JSON 커맨드를 요구하지 않으며 최종 공개 대상·보상·worker 모델을 표시한 게시 선택으로 동일 digest를 승인한다. 준비 중 프로젝트 파일이 바뀌면 차단한다.

로컬 설정은 서비스 origin/user/project에 묶인 project config와 requester session으로 관리한다. 게시 중단 후 같은 pending request를 재개한다. 새 AI 호출은 이전 대화를 상속하지 않으며 구독 인증 확인이 실패하면 자동 작성을 시작하지 않는다. public Git repository 생성 확인과 TIG 예치 확인은 구분한다. [대화형 사용법](../REQUESTER_QUICKSTART.md).

wizard 보상은 현재 사용자 요청에서 명시적으로 읽거나(`statedReward`) 따로 입력받아 session에 저장한다(P-069). 도구·모델·추론 수준도 사용자가 적은 값만 쓴다. 이미 공개/게시된 요청의 금액은 이 과정에서 변경하지 않는다. 설치 서버 주소가 달라지면 기존 token을 재사용하지 않고 다시 device pairing한다.
