# 서로 다른 AI 도구의 협업 절차

## 현재 제공 범위

이 저장소는 파일·Git·PR로 협업 상태를 공유한다. 상시 실행 중인 중앙 에이전트, 자동 작업 배정기, 예약 실행기는 없다.
조율 AI는 사용자가 요청할 때 최신 공유 기록을 조회하고 작업 제안, 의존성 확인, 충돌 점검, 리뷰 준비를 수행한다.
각 AI 도구는 같은 파일을 읽고 같은 산출물을 작성한다. 자동으로 다른 세션에 지시하거나 미업로드 작업을 볼 수는 없다.

## 기록의 기준

| 정보 | 기준 위치 | 갱신 시점 |
| --- | --- | --- |
| 제품 요구사항 | `docs/product/00_confirmed.md` 및 카테고리 문서; 초기 기준은 기획서 | 유찬의 제품 결정 시 |
| 공통 작업 규칙 | `AGENTS.md`, 이 문서 | 협업 절차 변경 시 |
| 작업 계약·담당자·선행 작업 | `docs/coordination/tasks/TH-xxx.md` | 배정/범위 변경 시 |
| 내부 협업 결정 | `docs/DECISIONS.md` | 유찬의 결정 시 |
| API·데이터 계약 | `docs/contracts/` (TH-003에서 최종 계약 확정) | 소비자/제공자가 합의한 계약 변경 시 |
| 진행 상태·인수인계 | 작업 브랜치의 작업 문서 | 시작, 중간 공유, 중단, 리뷰 요청 시 |
| 검토 가능한 변경 | PR diff, PR 검사 결과 | push 시 |
| 실제 병합 여부 | GitHub PR 병합 상태와 main 이력 | 병합 시 |

개인 AI 대화창은 공유 기록이 아니다. 대화 전문·내부 추론·토큰·비밀번호를 저장하지 않는다.
필요한 결정 이유, 코드 변경, 실제 검증 결과와 다음 행동만 기록한다.

## 배정과 실행

1. 조율 AI가 최신 main 및 열린 PR을 조회하고, 작업별 담당자·선행 작업·수정 범위를 비교한다.
2. 미배정 작업은 담당 제안으로 표시한다. 유찬이 배정을 결정하면 근거와 담당자/리뷰어를 작업 문서에 확정하여 공유한다. 팀원은 가용 시간·의견을 제시한다.
3. 1명당 구현 작업 1개를 진행한다. 리뷰는 병행 가능하다. 작업 하나에 수정 책임자 1명만 둔다.
4. 완료된 선행 작업을 가진 TODO 작업부터 시작한다. 10일 공개 베타 목표를 기준으로 날짜·결과물·의존성을 유찬과 확정한다. P-039에 따라 하루 가용시간 입력은 요구하지 않는다. 현재 배정·의존성은 WORKFLOW.md와 작업 문서를 따른다. 10일 표는 목표 일정이며 실제 상태와 구분한다.
5. 작업별 브랜치에서 상태를 IN_PROGRESS로 바꾸고 시작 기록을 commit/push한다. 가능한 한 이때 Draft PR을 열어 다른 AI가 작업을 발견하게 한다.
6. 중단하거나 의미 있는 진행이 있으면 인수인계 기록과 변경을 commit/push한다. 로컬에만 있는 변경은 공유되지 않았다고 명시한다.
7. 검증 후 상태를 REVIEW로 바꾸고 Draft를 해제한다. 상대방은 자기 AI로 리뷰를 보조받되 최종 병합·출시 결정은 유찬이 한다.
8. CI와 리뷰 조건을 만족하고 유찬이 병합을 결정하면 병합한다. 다음 조율 PR에서 병합 URL/커밋과 함께 DONE을 기록한다.

병합 전 REVIEW 표시는 정상이다. main에 REVIEW가 남아 있어도 PR 병합 사실을 확인하면 선행 작업 완료로 판단할 수 있다.
반대로 작업 문서에 DONE만 적혀 있고 병합 증거가 없으면 완료로 판단하지 않는다.

## 시작할 때 확인할 범위

AI는 다음 정보를 읽고 사용자에게 작업 ID, 범위, 의존성, 충돌 여부를 짧게 알린다.

```bash
git status --short --branch
git fetch origin
gh pr list --state open --json number,title,headRefName,author,isDraft,url
```

관련 PR은 `gh pr view <번호>`, `gh pr diff <번호>`로 확인한다.
필요하면 `git show origin/<작업브랜치>:docs/coordination/tasks/<작업ID>.md`로 원격의 진행 기록을 읽는다.
다른 작업을 보기 위해 현재 checkout을 임의로 전환하지 않는다.
`gh`가 없는 도구는 GitHub 웹이나 사용자가 제공한 PR 내용을 사용하고, 확인하지 못한 원격 상태를 명시한다.

현재 세션의 최신 사용자 지시를 우선 반영한다. 공유 규칙과 작업 계약은 최신 main이 기준이고, 진행 중 작업의 상태/인수인계는 해당 PR의 최신 브랜치가 기준이다.
main 갱신을 작업 브랜치에 반영할 때 먼저 변경 사항을 검토하고 미커밋 작업을 보존한다.
다른 checkout에서 조율 문서가 병합되었다면 자신의 담당 작업 시작 전에 그 변경을 받아야 한다.

## 충돌과 계약 변경

- 파일 범위가 겹치는 작업을 동시에 시작하지 않는다. 공통 파일은 별도 선행 작업으로 분리하거나 한 담당자가 먼저 변경한다.
- API 계약에는 필드 이름·타입·필수 여부·요청/응답 예시·상태 전이·오류·인증 조건을 포함한다.
- Web의 mock과 서버 구현은 동일한 계약 파일을 참조한다. 계약 변경 PR에는 소비하는 작업 ID와 영향을 적는다.
- 루트 패키지 설정, lockfile, CI, 공통 타입, DB migration은 공통 파일로 취급한다. 작업 범위에 소유자를 명시한다.
- 상대 작업의 승인이 필요한 부분은 BLOCKED와 구체적인 질문을 기록한다. 독립적인 부분은 별도 작업으로 진행할 수 있다.
- 오래된 진행 기록을 완료나 실패로 추정하지 않는다. 마지막 확인 시각을 표시하고 담당자의 갱신을 요청한다.
- Git과 PR은 원자적인 작업 잠금이 아니다. 자동 중복 실행 방지는 아직 구현되지 않았다.

## 인수인계 예시

아래는 형식 설명용 예시이며 실제 구현 결과가 아니다.

```text
작업: TH-004
상태: REVIEW
담당자: rhkim00
브랜치: feat/TH-004-web-shell
기준 main: <작업 시작 시 SHA>
최신 변경: <현재 기록 이전의 코드 커밋 SHA>
사용 도구: <도구명>, 모델: <확인 가능할 때만>
변경: Task 상세 화면과 계약 기반 mock 연결
참조 계약: <docs/contracts/파일 경로와 기준 커밋>
검증: <실제 명령> → <통과/실패>; API 실제 연결은 미검증
결정: <D-xxx 링크 또는 없음>
장애물: 없음
다음 행동: timeistoken이 오류 상태와 API 계약 일치 여부 리뷰
PR: <URL>
```

기록 자신이 포함될 커밋 SHA를 미리 적으려 하지 않는다. 코드 커밋을 먼저 기록하거나 PR 최신 head로 추적한다.
도구/모델 정보는 사람이 확인한 참고 정보다. 실제 모델 사용에 대한 Execution Proof가 아니며 Tokenisgold 제품의 실행 증명과 별개다.

## 조율 AI의 결과 보고

매 조율 시 다음만 정리한다.

- 확인한 main SHA, 열린 PR과 확인 시각
- 각 사람의 진행 작업, 검증/리뷰 상태와 근거 링크
- 겹치는 파일·계약 변경·막힌 선행 작업
- 각 사람이 다음에 할 작업 1개와 완료 조건

도구가 자동으로 AGENTS.md를 읽는지는 가정하지 않는다. 모든 AI 세션은 START_HERE.md의 공통 시작 지시문으로 시작한다.
